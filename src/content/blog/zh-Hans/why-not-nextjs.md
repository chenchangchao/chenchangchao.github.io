## 一、视频字幕整理

### 00:00–00:36｜项目背景：一个看起来很简单的 Survey 系统

大家好，我是前端小卒。

公司内部要做一个 Survey 项目，也就是一个问卷系统。需求刚出来的时候，第一反应很容易是：这不就是前台填表、后台配题，最后看统计吗？

用 React 写页面，Next.js 起项目；表单提交用 Server Actions；接口少的地方直接用 Route Handler；数据库接一下 Prisma，差不多就能跑了。

但最后，我选择的是 **NestJS + TanStack**。

### 00:36–01:20｜先说清楚：否定的不是 Next.js 本身

我觉得 Next.js 不能做全栈吗？当然不是。

App Router 已经稳定很多年，Server Actions 也越来越成熟，相关工具链也进入了默认构建路径。你再说“Next.js 不成熟”，其实已经有点脱离现实。

我真正否定的是：在一个主要复杂度明显落在业务后端的项目里，用页面框架去承担后端架构的职责。

这个区别非常重要。

### 01:20–02:08｜Next.js 的强项仍然围绕 React 应用展开

Next.js 的全栈能力，本质上还是围绕 React 应用展开的。

它非常适合官网、内容站、营销页、电商前台，以及强依赖 SEO 的页面。它能把页面渲染、数据获取、缓存、路由、构建和部署整合得很好。

但对于一个业务系统来说，问题并不只是“能不能提交一个表单”。

问卷也不只是一张表单。一个问卷会被创建、编辑、预览、发布、填写、回收和统计。

### 02:08–03:04｜问卷系统真正复杂的是业务模型

问卷有版本，有发布状态，有历史数据，还可能有权限控制和逻辑跳转。

问题类型如何扩展？选项如何存储？必填、校验和跳转逻辑怎么表达？答卷提交以后能不能修改？统计口径如何定义？

这些问题的复杂度，并不主要来自页面，而来自后端业务模型。

如果从第一天就不阻止项目进入一种状态：Server Actions 里面混着鉴权、校验、审计和日志；Route Handler 里再补一点导出和回调；业务逻辑散落在前端页面的文件夹中——那么它表面上是一个 Next.js 应用，实际上已经是一套被页面结构牵着走的后端系统。

这就是我否决 Next.js 作为这个项目核心架构的原因。

### 03:04–04:02｜“可以写后端”不等于“适合作为后端边界”

Next.js 当然可以写后端。

Route Handler 可以处理请求，Server Actions 可以做表单提交，middleware 可以做鉴权，一些简单接口都能实现。

但工程最怕的不是“实现不了”，而是没有明确边界。

当业务持续增长以后，你仍然需要回答：

- 业务模块如何拆分？
- Controller、Service、Repository 如何分层？
- DTO 如何约束输入和输出？
- 错误码怎么设计？
- 鉴权、审计、日志和事务放在哪里？
- 第三方系统和自动化任务如何复用这些业务能力？

框架给你的只是便利，不是约束。

### 04:02–05:00｜Server Actions 很好，但它不是业务 API 的替代品

Server Actions 很好，它让很多 mutation 变得非常自然，比如表单提交和页面内操作。

但我不愿意在 Survey 这种项目里，把核心业务动作都压到 Server Actions 上。

因为“创建问卷”“发布问卷”“提交答卷”“生成统计”等动作，未来不一定只来自当前网页。

它们可能来自后台管理端、移动端、第三方系统、自动化任务，或者别的入口。

所以我更愿意从一开始就把它们设计成稳定的 HTTP API，而前端只是这些 API 的消费者之一。

Server Actions 适合贴近 UI 的 mutation，但不应自然地成为复杂业务系统的边界本身。

### 05:00–06:00｜页面框架的心智模型会反过来影响业务架构

Next.js 给你的便利，很容易让人沿着页面结构组织业务。

今天一个入口放一个 Server Action，明天在 Server Component 里查数据，后天再在 Route Handler 里补接口。

每个人写的代码都能工作，但不同人的理解会逐渐分叉。

业务逻辑会散落在 action、handler、component、lib 等目录之间。这个问题不是 Next.js “不能做”，而是它对业务后端边界提供的约束不够强。

### 06:00–07:18｜复杂后台系统中，RSC 的收益未必覆盖认知成本

另一个需要持续回答的问题，是 Server Components 和 Client Components 的边界应该放在哪里。

什么时候需要 `use client`？什么时候使用 server-only？什么时候使用 cookie、缓存或 hook？什么时候需要 revalidatePath，什么时候使用 revalidateTag？

对于内容站和首屏性能敏感的页面，这些能力很有价值。

但问卷后台最耗时间的，往往不是首屏的极致优化，而是字段联动复杂、筛选条件复杂、表格分页排序复杂，以及权限和状态流转复杂。

如果一个项目不需要公开内容分发，不强依赖 SEO，那么它的主要矛盾就是业务复杂度，而不是渲染模式。

框架选择应该围绕主要矛盾，而不是围绕流行度。

### 07:18–08:26｜NestJS 把后端问题提前摆到桌面上

在这个项目里，我会把后端拆成比较清晰的模块，例如：

- SurveyModule
- QuestionModule
- ResponseModule
- PermissionModule
- NotificationModule

每个模块下面有 Controller、Service、DTO，以及 Repository 或 Data Access 层。

这套结构看起来没有 Next.js 那么轻，但它对长期维护更友好。

它会迫使团队提前回答几个重要问题：接口是什么？输入输出是什么？权限在哪里判断？业务规则属于哪个模块？错误怎样表达？

这些问题越早明确，后续需求越不需要靠猜。

### 08:26–09:26｜为什么前端选择 TanStack

前端更像一个典型的富交互后台应用，所以 TanStack 解决的问题非常直接。

- TanStack Router 负责前端路由；
- TanStack Query 负责服务端数据状态；
- TanStack Form 负责表单状态；
- TanStack Table 负责表格、筛选、分页和排序；
- URL Search Params 用来表达筛选、分页和排序状态。

后端暴露稳定的 API，前端只需要把页面和交互做好，不必同时承担服务端执行和缓存策略的心智负担。

### 09:26–10:18｜全栈一体化，不等于工程更简单

现在大家很喜欢讲 full-stack framework，尤其是 AI 流行以后。

因为前后端分离看上去会带来接口对接、类型同步、状态管理、部署链路和重复校验等问题。

但把所有代码放进一个仓库，不等于架构变简单。有时候只是把边界藏起来了。

真正的工程简单，不是文件少，而是每一种变化发生时，你能快速知道它应该改在哪里。

产品提出一个需求时，我希望第一反应是去找对应的业务模块，而不是在 component、action 和 route.ts 之间来回翻。

### 10:18–11:10｜NestJS + TanStack 不酷，但边界清楚

NestJS 加 TanStack 没有那么酷，也不是所谓的“一把梭”。

它会多写一些 Controller、DTO、Service 和 API 调用，但它换来的是清晰的职责边界。

我并不是想表达 Next.js 不好，更准确地说：**框架成熟，不代表你的架构成熟；框架能力强，也不代表它适合承载所有类型的后端复杂度。**

Next.js 最大的问题不是能力不够，而是它太容易让团队在业务边界还没想清楚的时候，就顺着页面结构开始写代码。

### 11:10–12:16｜最终结论

对于这个 Survey 项目，复杂度不在页面，而在问卷模型、答卷模型、权限模型，以及发布和状态流转。

所以最终方案是：

- **NestJS**：负责后端业务；
- **TanStack**：负责前端富交互；
- 通过清晰的 **HTTP API** 协作。

这个方案看起来传统一点，但传统不一定是坏事。

框架选择应该围绕主要矛盾，而不是围绕流行度。对于业务后端复杂的项目，边界清晰往往比“一体化”更重要。

谢谢观看。

## 二、内容解析

### 1. 视频真正讨论的不是“Next.js 能不能写后端”

作者并没有否定 Next.js 的全栈能力，而是在区分两个问题：

1. **技术能力问题**：Next.js 能不能提供接口、鉴权、数据库访问和数据修改？答案是能。
2. **架构适配问题**：当核心复杂度在后端业务模型时，Next.js 是否仍是最合适的组织方式？作者的答案是否定的。

这是一种很重要的工程判断：**可实现性不等于适配性**。

### 2. 选择框架，要先定位系统的“主要复杂度”

作者把系统分为两类：

- 主要复杂度在页面渲染、内容分发、SEO 和首屏体验：Next.js 很合适；
- 主要复杂度在业务规则、权限、状态机、事务和多入口复用：独立后端更合适。

Survey 项目表面是“填表”，本质上却包含问卷定义、版本管理、发布、答卷、权限、统计和流程状态，因此更接近一个业务平台，而不是一个页面项目。

### 3. Server Actions 的合理边界

视频对 Server Actions 的态度并非排斥，而是限制其职责：

- 适合：和页面强绑定、范围局部、无需被其他客户端复用的 mutation；
- 不宜直接承担：核心领域动作、跨客户端共享能力、长期稳定 API，以及复杂事务和权限逻辑。

可以把它理解为：Server Actions 是优秀的 **UI 适配层**，但不一定应该成为系统的 **领域边界**。

视频对 Server Actions 的剖析非常精准：它是 RPC 的语法糖，用于优化 UI 交互，而不是微服务或业务 API 的终态。

很多团队用 Server Actions 直接连数据库做核心业务，这违反了单一职责原则。一旦你的系统需要接入一个小程序端，或者需要写一个定时跑批任务，紧耦合在 Server Actions 中的代码将变得毫无复用性可言。
### 4. “一体化”可能只是隐藏了复杂度

全栈框架减少了仓库数量、部署单元和接口样板代码，但并不会让业务复杂度消失。

如果缺少主动设计，复杂度可能从显式的 Controller、Service、DTO，转移到散落的 Server Actions、Route Handlers、Components 和工具函数中。

代码数量少，不一定意味着认知负担低；目录看起来简单，也不一定意味着业务边界清晰。

### 5. NestJS + TanStack 的互补关系

这个组合体现的是明确分工：

- NestJS 解决模块化、依赖注入、DTO、鉴权、拦截器、异常处理和后端分层；
- TanStack Router / Query / Form / Table 解决后台应用中的路由、请求状态、表单和表格交互；
- HTTP API 作为稳定契约，使 Web、移动端、自动化任务和第三方系统都可以复用后端能力。

它牺牲了一部分“全栈一体化”的便利，换取了更强的边界感和可扩展性。

### 6. 页面驱动 (UI-Driven) vs 领域驱动 (Domain-Driven)

- Next.js 的文件系统路由（File-system based routing）本质上是一种页面驱动的架构。这在展示型应用中是降维打击。但在复杂的 B 端业务中，系统的核心是领域模型（Domain Model）。
- 问卷系统是一个典型的复杂领域：它包含实体（问卷、题目、选项）、聚合根（一份包含所有逻辑的完整问卷）、值对象和复杂的领域服务（发卷逻辑、算分逻辑）。如果用 Next.js，开发者会本能地沿着 /app/survey/page.tsx 的思路去写代码，最终导致领域逻辑被 UI 路由绑架。NestJS 则强制开发者从 Module（领域）开始思考。

## 三、AI的注解

### 注解 1：作者的核心观点是对的，但不应被理解成固定技术结论

我认同视频最关键的一句话：**框架选择要围绕主要矛盾。**

不过，“业务复杂就一定要 NestJS”也不成立。真正起作用的不是 NestJS 这个名字，而是团队是否明确建立了领域层、应用层、基础设施层和接口层。

即使用 Fastify、Hono、Bun，甚至继续使用 Next.js，只要主动建立清晰的模块和依赖方向，同样能做出可靠架构。反过来，即使用 NestJS，如果所有逻辑都堆进 Service，也一样会失控。

### 注解 2：Next.js 也可以采用 BFF，而不是非黑即白

实际项目中还有一种折中方案：

- 独立后端负责领域逻辑和稳定 API；
- Next.js 负责 SSR、页面路由和 BFF；
- Server Actions 只做薄薄的页面适配，不承载核心业务。

因此，真正要避免的并不是 Next.js，而是让页面层反向定义整个业务系统。

### 注解 3：作者强调 DTO 很重要，但“契约”还可以更进一步

如果前后端使用 TypeScript，除了 DTO，还可以使用：

- OpenAPI + 自动生成客户端；
- Zod / TypeBox 等共享 schema；
- tRPC（适合只有 TypeScript 客户端的内部系统）；
- 契约测试和 API 版本策略。

这样可以减少视频中提到的接口对接和类型同步成本，同时保留独立后端的边界。

### 注解 4：Survey 项目最值得优先设计的是领域模型和状态机

技术栈之前，更应该先明确：

- 问卷草稿、已发布、已关闭之间如何流转；
- 发布后能否编辑，编辑是否生成新版本；
- 答卷与问卷版本如何绑定；
- 匿名、实名、组织权限如何建模；
- 逻辑跳转规则如何表达和执行；
- 统计结果是实时计算还是异步聚合；
- 重复提交、并发修改和幂等如何处理。

这些设计才决定系统后续是否容易维护。框架只是在帮助这些模型落地。

### 注解 5：对 AI 编程时代尤其有启发

AI 很擅长快速生成页面、Route Handler 和 Server Action，因此团队更容易在短时间内得到“能运行”的产品。

但 AI 也会放大缺乏边界的问题：如果没有明确模块规则，它会不断沿用已有目录和局部模式，最终生成大量彼此能运行、整体却难维护的代码。

所以在 AI 辅助开发中，架构约束反而更重要。应把模块职责、依赖规则、API 契约、错误格式和代码模板写进项目规范，让 AI 在约束内生成代码。

### 注解 6：结合你的技术栈，我更推荐 Bun/Fastify，而不必照搬 NestJS

对你熟悉的技术栈而言，这个视频的思想可以落地为：

```text
apps/
  web/                 # Vite + React + TanStack Router/Query/Form/Table
  api/                 # Bun + Fastify
packages/
  contracts/           # TypeBox/Zod schema、API 类型、错误码
  domain/              # 问卷、答卷、权限、发布状态等领域逻辑
  db/                  # Drizzle ORM、迁移、Repository
```

后端可以按领域拆分：

```text
src/modules/
  surveys/
  questions/
  responses/
  permissions/
  analytics/
  notifications/
```

每个模块内部保持 `route/controller → service/use-case → repository` 的单向依赖。这样既保留 Bun + Fastify 的轻量和性能，也获得视频所强调的边界清晰。

## 四、一句话总结

**Next.js 并不是不能做全栈；当系统的主要复杂度来自业务后端时，不应该因为页面框架“什么都能做”，就让页面结构决定整个系统架构。**
